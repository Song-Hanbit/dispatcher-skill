# Dispatcher Memory

## Current Implementation

The dispatcher app lives in `dispatcher_app/server.py` and uses only Python standard library modules.

It includes:

- `ThreadingHTTPServer` web server.
- Browser UI files under `dispatcher_app/templates/` and `dispatcher_app/static/`.
- SQLite store at `data/dispatcher.db`.
- External dispatcher loop in `dispatcher_app/dispatcher.py`.
- Codex manager runner in `dispatcher_app/codex_runner.py`.
- Dispatcher-owned worker client and runner in `dispatcher_app/worker_client.py` and `dispatcher_app/worker_runner.py`.
- Host-side reboot request watcher in `dispatcher_app/reboot.py`.
- SQLite-backed global runtime mutex helpers in `dispatcher_app/runtime_lock.py`.
- Password login with an in-memory session cookie.

The queue UI uses `templates/index.html`, `static/app.css`, and `static/app.js`. The index document title and visible header are rendered server-side from the repository folder name, with a safe fallback. It has status lanes containing task cards. Cards are collapsed by default and show only `#id title`; clicking the title toggles details. Expanded cards use natural content height with no internal card scrollbar. Manager result text inside expanded task cards is rendered as escaped, limited Markdown. Lanes adapt their viewport height to the largest expanded card in each row and scroll internally when additional cards overflow. On compact viewports, Activity, Agent status, New task, Queue, Directory, and cards are all collapsed by default. On larger viewports, Activity, Agent status, New task, and Queue open by default while Directory and cards remain collapsed. Panel defaults are set once at initial load from the viewport width, then user toggles are left alone on later resizes. Panels can be opened from their header labels without visible `[+/-]` markers. An Activity panel sits to the left of Agent status and renders one internal card per manager. Each manager card acts like a shared task room: it shows the user task request plus manager and worker events for that manager's current/latest task, so workers appear inside the manager conversation instead of as separate Activity cards. Manager cards show the current task while running, then keep the latest task conversation after the manager becomes idle until that manager claims the next task. The Activity card uses a compact chat-style treatment: agent header with status pill, subtle state rail, task strip, message bubbles, and actor-colored action rows for command/file-change/delegation details. The card uses Activity-specific states (`current task`, `latest task`, or `empty`) instead of duplicating Agent status runtime labels. The chat contains the task request plus role-specific message/result/error events, and message bubbles use distinct subject classes/backgrounds for user, manager, worker, operator, and system speakers; `task_failed` is rendered as a manager error bubble rather than falling back to system gray. Command execution, file change, and worker delegation item events are coalesced by item id and shown as single non-chat status lines, changing from `running: {detail}` to `ran: {detail}` when the matching completion event arrives. Dispatcher-owned worker reports are emitted as `worker_stream` chat bubbles so report text appears in Activity, not only in JSONL audit logs; worker commands and file changes streamed by `worker_runner.py` are promoted to `worker_command` and `worker_file_change` Activity rows. Worker activity now comes from dispatcher-owned worker requests and the worker Codex process, not from Codex harness subagent markers. The browser keeps a display-only fallback for already persisted raw `item.*: collab_tool_call` messages, rendering them as manager-side delegation details without updating worker state or logs. The `running`/`ran` state text is colored separately from the detail. Detail text can be collapsed into one clipped line with a separately colored `...` marker, or expanded to show the full command/file/delegation content. The collapsed text is measured against the rendered Activity card width and trimmed in the browser so the visible text plus marker stays inside the card instead of increasing intrinsic width. Activity panel internals are width-constrained and clip long collapsed details so the panel does not create horizontal scroll. Lifecycle events such as task claim/start are omitted from the manager chat, stderr is hidden from UI, and JSON manager decision payloads are normalized to their user-facing summary/result text. Expanded queue cards still show task events below the controls, but `item.*` manager, worker, and operator action events are excluded there; queue lane/card/event elements are width-constrained so long event log strings wrap inside the card instead of creating lane-level horizontal scroll. Agent status cards also toggle open/closed; collapsed agent cards show only the agent name and runtime status, and each card uses a stable manager/worker/operator/system actor class so its background tone matches Activity speaker colors while the status stripe and pill still show runtime state.

The left-side Agent status panel includes a Directory section populated from `/api/directory`; the section is collapsed by default and can be opened from its header label. Collapsing Agent status hides only the agent card list, so the Directory section remains visible and independently collapsible. Directory toggle markers are hidden, and directory rows default collapsed in the browser; the server still fetches all non-excluded entries without a hard cap, and expanding a directory reveals its descendants. The directory tree and header title use the operator workspace root from `DISPATCHER_WORKSPACE_ROOT`; existing installs without that value fall back through `DISPATCHER_REPO` and then the server process cwd. The tunnel helper persists and exports the workspace value from the operator cwd that started the skill. Directory data no longer shows a truncation notice; dot-prefixed directories such as `.git/`, `.codex/`, and `.agents/` are included, while generated `__pycache__/` directories and dot-prefixed regular files other than `.gitignore` remain hidden.

The browser UI prefers live updates through `/api/stream`, a Server-Sent Events endpoint that emits an initial `snapshot` and later `update` events when a composite UI revision changes. The revision includes latest SQLite event id, task row count/latest task update time/task row digest, manager runtime row count/latest runtime update time/runtime row digest, runtime lock row count/latest lock update time/lock row digest, and local `agents.json` mtime. The row digests let SSE detect server-side task status changes even if no event row is added or `updated_at` does not advance. The stream also sends a periodic `update` heartbeat every 5 seconds so a connected browser refreshes even if a revision edge is missed. `static/app.js` connects with `EventSource`, force-refreshes task/agent/directory/runtime-lock data after stream events, and also keeps a 0.5-second safety polling loop active so the board follows server-side changes even if the SSE connection stalls. Browser rendering ignores stale refresh responses, coalesces overlapping forced refreshes into one follow-up load, skips unchanged panel re-renders, and sequences lane-height animation-frame updates so older renders cannot overwrite newer board state. The header status line tracks the last successful load time in JavaScript and updates the displayed elapsed time every second without a server request. A compact header lockline reads `/api/runtime-lock` and shows whether the global execution lock is idle, task-owned, operator-owned, or expired without exposing the fencing token. The external dispatcher loop defaults to a 0.5-second pending-task poll interval.

New tasks enter the `Inbox` lane by default, or can be created directly in `pending` from the New task form's `Add to Pending` button. Active managers can also suggest optional Inbox todo candidates with `python3 -m dispatcher_app.task_client suggest --task-id <current_task_id> --manager-role-key <manager> --items-file <path>`; this path requires the same manager/task/runtime-lock ownership checks as worker requests, requires each suggested item to have a title or description, always creates `inbox` rows with no `queued_at`, and records events on both the suggested cards and source task. Queue lanes render cards latest-first within the lane: Inbox by `created_at`, Pending by durable `queued_at` with legacy null `queued_at` rows after real queued rows, and in-progress, approval, done, failed, and canceled states by `updated_at`, with `id DESC` as the stable tie-break. Pending claim order remains FIFO by the durable `queued_at` timestamp set when a task enters or re-enters `pending`, not by task id. Direct-to-pending creation, Inbox `Queue`, approval retry, manual retry, and expired lease reclaim all set a fresh `queued_at`; dispatcher claim order stays oldest-first even though the Pending lane displays latest-first. The title field is optional; titleless cards display as `#id` with no placeholder title. The user can `Queue` an Inbox card into `pending`, `Move to form` to delete the Inbox card after a successful delete request and load its editable fields into the New task form, or `Delete` it permanently; delete does not create a `canceled` task. Bodyless task actions do not send empty JSON request bodies, and the server drains any POST body before responding so Cloudflare Quick Tunnel does not see origin EOF during action requests. Task deletion removes related worker requests before deleting task/event rows. Needs Approval cards show the manager-produced summary/reason in the result area and include an in-card note field plus `Approve` action; approving appends a labeled user approval note to `acceptance_criteria`, records an approval event, and requeues the task for the next manager run. `failed` and `canceled` cards share the `Closed` lane, with different left-stripe colors and a status line in expanded cards.

The New task form has `Add task`, `Add to Pending`, and `Clear` controls. `Clear` resets all form fields to their defaults and returns focus to the title input. A lightweight Bash terminal was briefly prototyped under this panel, but it is now obsolete and removed from the active UI/API because it exposed authenticated browser-driven command execution.

Runtime data under `data/` is ignored by Git. The per-repository agent registry at `dispatcher_app/agents.json` is also ignored by Git and generated by `dispatcher_app/agent_registry.py` during initialization or first direct server/dispatcher use; it starts with empty operator, manager, and worker handles so packaged skills do not ship another repository's Codex session IDs. Manager conversation records are appended to `data/agent_conversations/<role_key>.jsonl` with request, Codex stdout/stderr JSONL event, recoverable runner warning, and final response records. Dispatcher-owned worker conversation records are appended to `data/agent_conversations/<worker.role_key>.jsonl` by `worker_runner.py` with the worker prompt, streamed Codex events, and final report. Manager-side `collab_tool_call`, `WORKER_HANDLE`, and `WORKER_ACTIVITY_JSON` compatibility markers no longer copy records into worker logs or update worker session state; worker logs and worker session keys are owned by dispatcher-owned worker requests. If `codex exec` exits non-zero but wrote a valid final manager decision file, the runner accepts that decision and records the non-zero exit/stderr as `runner_warning` instead of failing the task. Missing or unparseable final decision files still fail, but known non-actionable Codex CLI stderr noise such as plugin manifest warnings, skill icon warnings, file watcher unwatch warnings, and Cloudflare challenge HTML is filtered out before choosing the user-facing failure text. Task event messages are capped for UI/runtime safety, but structured command/file-change events are kept as valid JSON; long command payloads are truncated inside the `command` field rather than slicing the whole JSON string. Runtime restart requests use `data/reboot_requests.jsonl`, with watcher state and result events in `data/reboot_state.json` and `data/reboot_events.jsonl`. Managers do not call `dispatcher_app.reboot request` directly from a task. When runtime restart is needed, the manager adds an operational final-result marker such as `REBOOT_AFTER_TASK restart-dispatcher <short reason>` after implementation, docs or memory updates, and verification are complete. The dispatcher strips `REBOOT_AFTER_TASK` lines from the stored user-facing task result, marks the task `done`, then appends validated reboot request records after the completion commit. Invalid markers create task events and do not fail an otherwise successful task. After any reboot request is appended, the dispatcher treats unprocessed records beyond `data/reboot_state.json`'s offset as a reboot barrier and pauses new pending task claims until the watcher processes them, so delayed manager-requested restarts cannot interrupt the next pending task. The reboot watcher defers dispatcher-affecting due requests (`restart` and `restart-dispatcher`) while any task is `in_progress`, any manager runtime row is non-idle, or any unexpired runtime lock exists. `restart-server` and `restart-reboot` remain available for single-process restarts that do not stop the dispatcher.

Worker execution is now dispatcher-owned but manager-invoked. The dispatcher still dispatches queued tasks only to the manager and passes a filtered `worker.*` catalog. When a worker is useful, the manager writes bounded instructions to a prompt file and runs `python3 -m dispatcher_app.worker_client call --task-id <id> --manager-role-key <manager> --worker-role-key <worker> --prompt-file <path>`. The worker client can queue a `worker_requests` row only while the task is `in_progress`, the manager runtime row is busy for that task, and the global runtime lock is still owned by the same manager/task pair. The dispatcher loop services pending worker requests, runs `worker_runner.py`, streams worker command/file-change/message events into Activity, writes worker JSONL audit records, and stores dispatcher-owned worker session keys with `key_status=dispatcher_ready`. `worker_requests` also persists `heartbeat_at` and concise `progress`; while `worker_runner.py` is blocking, the dispatcher heartbeats the running request so Agent status can show the worker's active task/request and recent liveness without estimating completion time. Manager and worker Codex subprocess runs are cancellation-aware: dispatcher passes task-status `cancel_check` callbacks when the runner supports them, `run_codex_streaming()` terminates the subprocess if the task is canceled or disappears, and normal manager/worker work events are no longer appended after cancellation. A canceled task remains `canceled`; background manager completion/failure/approval transitions do not overwrite it, worker completion/failure storage rechecks parent task status before inserting terminal worker activity, and canceled worker requests are finalized as failed with canceled progress. Only one pending or running worker request is allowed per manager task. Agent status derives worker `busy`/`idle`/`error` from active worker requests first, then falls back to the latest structured `worker_delegation` event; stale running events from completed tasks display as idle, and terminal worker request rows are normalized to completed/failed/canceled progress text instead of showing stale running text.

`scripts/context_compact.py` provides agent-side context compression and Markdown handoffs between operator and manager agents. It instructs agents to compress their own working context into durable, receiver-useful facts before writing handoffs. It writes one handoff file per agent role under `memory/context-compression/`, supports receiver acknowledgment that purges read handoffs, includes an approved-only `purge-tasks` workflow that snapshots current UI cards into compressed context before clearing task/event rows, and includes an approved-only `purge-runtime-logs` workflow that summarizes `data/agent_conversations/` and `data/codex_runs/` metadata into compressed context before deleting only regular files under those log directories. After required safety preconditions, including operator runtime audit and mutex acquisition, nonempty unread handoff entries addressed to the current agent are processed before other substantive work: read, catalog useful durable facts into `memory/*.md`, update `memory/memory.md` if the catalog changes, then acknowledge/purge. Runtime log purging and handoff cataloging omit raw log lines, stdout/stderr, full transcripts, prompts, command output, secrets, full JSON records, and non-actionable detail from memory.

The global execution mutex is stored in SQLite `runtime_locks` with resource `global_execution`, owner plane/id, optional task id, fencing token, heartbeat, lease expiry, and updated timestamp. Dispatcher-managed work acquires the lock before claiming a pending task, binds the claimed task id to the lock, heartbeats it alongside the task lease and manager runtime, and releases it by fencing token after the task reaches a terminal or approval-paused state. If the lock is held by operator work, pending tasks remain unclaimed until a later poll. Operators use `python3 -m dispatcher_app.runtime_lock acquire|heartbeat|release` with a token file for every operator task after the initial audit/lock-status check. UI reads and task creation remain outside the mutex, and Agent status marks Operator busy while an active operator-plane lock is held.

## Auth

The app has a single-user password gate. Unauthenticated users see `/login`; unauthenticated API requests return `401`. Login sets an HttpOnly `dispatcher_session` cookie. Server restart invalidates active sessions because the token is generated in memory.

The password currently exists in code for app simplicity. Do not move secrets into `memory/`. A later hardening pass should read it from an environment variable.

## Task Flow

1. User creates a task through the form or `POST /api/tasks`; it enters `inbox` by default, or `pending` when the payload status is `pending`.
2. User queues the task into `pending` or deletes it permanently.
3. The external dispatcher process first acquires the `global_execution` runtime lock, then claims the oldest `pending` task by `queued_at` only when the selected manager runtime is `idle`.
4. For unapproved risky work, the manager prompt requires a `needs_approval` decision before performing the risky action, so the manager can supply the approval summary and reason.
5. The dispatcher calls the manager through `codex exec` or `codex exec resume` with non-interactive approval policy and `workspace-write` sandbox, then records selected stdout `item.*` manager actions/messages as Activity events. Command execution, file change, and worker delegation items use separate Activity event types so the browser can replace `running` with `ran`. If the manager queues a dispatcher-owned worker request, the dispatcher services that request while the manager waits and emits worker command/file-change/message events into the same manager Activity room. Stderr remains in JSONL audit logs but is hidden from UI.
6. Normal or approved tasks are completed from the manager decision and marked `done`; recoverable Codex tool-call stderr does not fail the task when a valid final manager decision exists.
7. If the manager result contains validated `REBOOT_AFTER_TASK` markers, the dispatcher appends the corresponding host-side reboot requests only after the task has been marked `done`.
8. While those reboot request records remain unprocessed, the dispatcher pauses new pending task claims and resumes only after the reboot watcher advances `data/reboot_state.json`.

Run the loop separately from the web server:

```bash
python3 -m dispatcher_app.dispatcher --db data/dispatcher.db
```

The default dispatcher poll interval is 0.5 seconds. Override it with `--poll-seconds` when slower polling is needed.

The dispatcher does not reclaim expired leases for task IDs it is actively running in the current process. This prevents long manager calls from making an in-progress card appear back in Pending while the manager is still working. If the dispatcher process dies, a restarted dispatcher has an empty active set and can still reclaim expired leases.

Risk approval is manager-mediated: the dispatcher no longer pauses tasks through a pre-manager keyword match, so the Needs Approval card can contain the manager's own summary and reason.

## Verification

Manual verification should cover:

- Login page appears before authentication.
- Wrong password returns `401`.
- Correct password reaches the home page.
- New task enters `Inbox`.
- Inbox `Delete` removes the task without creating a `canceled` card.
- Inbox `Queue` moves the task into dispatcher processing.
- Normal task reaches `done`.
- Risky task reaches `needs_approval`.
- Approved risky task returns to the queue and reaches `done`.
